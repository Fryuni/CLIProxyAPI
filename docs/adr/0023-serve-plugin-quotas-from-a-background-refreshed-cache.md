# Serve plugin quotas from a background-refreshed cache

Live quota checks often fail because the upstream rate-limits them. Previously, each call to `GET` or `POST /v8/management/plugins/:id/quota` fetched the quota live, and a failed fetch returned only a 502. The management handler now keeps the last successful fetch for each plugin and credential in memory. Every 2 minutes, it probes the default quota plugin of each enabled credential, plus every plugin and credential already in the cache. A failed probe keeps the previous value and logs a warning. API calls return the cached value with an `X-Quota-Fetched-At` header. Only a credential with no cached value is fetched live, and if that fetch fails the call still returns a 502. Concurrent requests for the same uncached value share one upstream fetch, so a burst of requests cannot itself trigger the rate limit.

A cached value is valid only while the quota request inputs that the plugin receives (provider, metadata, and attributes) stay the same. Rotating token fields, such as access, refresh, and ID tokens and their expiry times, are left out of that fingerprint. A routine token refresh therefore keeps the cached fallback, while a change of account, project, or API key forces a new fetch. Credential versions are not used, because every token refresh bumps them. A successful quota reset drops that credential's cached values and detaches probes still in flight, so neither the cache nor a later reader can receive values from before the reset. `X-Quota-Fetched-At` is added to the CORS exposed headers so browser management clients can read it. The cache also forgets credentials that no longer exist.

The deprecated v0 routes keep their contract, as `AGENTS.md` requires. `/v0/management/plugins/:id/quota` shares the handler but still fetches live, and `/v0/management/quota/fetch` is unchanged. A v0 reset only drops the internal cached values. This is a deliberate fork addition under [ADR-0003](0003-minimize-fork-divergence.md), kept within the management handler.

The management panel's built-in Claude card bypasses plugin quotas: it reads Anthropic's OAuth `usage` and `profile` endpoints through `/v8/management/requests/api-call`, so the original cache did not protect it from rate limits. Cache those canonical credential-backed GET requests in the same handler-owned cache, retain their raw APICall response shape and observation timestamp, and warm enabled Claude OAuth credentials when the server attaches its dependencies and every 2 minutes thereafter, even without plugins; launch individual probes independently so a stalled request cannot hold up other credentials or future refresh cycles. Completed Claude probes, including failures, are shared until the next refresh is due to prevent UI retries from hammering upstream; preserve the last success on failure, keep token-rotation and account-replacement safeguards, and leave v0 and custom APICall requests live (an empty in-memory cache still cannot supply a successful value until upstream permits a probe).

A scheduled Claude refresh supersedes an unfinished probe: waiting readers follow its replacement, obsolete work is canceled, and an obsolete result cannot publish even if its replacement fails. This is lifecycle cancellation when work is superseded, without adding connection or response deadlines. Only the complete headers sent by the built-in card qualify for caching: usage requires its JSON `Accept` header, while the canonical profile request omits `Accept`; incomplete or modified requests continue through generic APICall.

An added `Accept` header also makes a profile request noncanonical and keeps it live. The SDK's token-only requester uses a handler constructed without a quota refresher, since it exposes neither quota endpoints nor a way to stop that worker; full management handlers retain their normal refresh lifecycle.

Use one canonical header definition for request matching and upstream probes, including the management card's exact `claude-cli/2.1.280 (external, cli)` user agent and the profile endpoint's omission of `Accept`. Executor device defaults do not change that management contract; requests with another user agent or duplicate case variants of a header stay live.
