# Upload request logs to a bucket

Request logs live only on the instance's disk, so they are lost when an ephemeral instance is replaced. The new `observability.logs.request-log-bucket` setting (legacy key `request-log-bucket`) takes a `gocloud.dev` bucket URL. The `gcsblob`, `s3blob`, and `fileblob` drivers are linked in, and credentials come from each provider's standard environment. Logs are still written locally first. A background uploader then copies each completed request or error log to the bucket under its file name and deletes the local copy. Local names are unique only within one directory at one time, while instances can share a bucket and a name can recur after an earlier upload. Uploads therefore use conditional creates and never replace an existing object. On a collision, the log is stored under the next sequenced name (`prefix_N-id.log`, as for local collisions), which keeps the request ID suffix. If deleting the local copy fails after an upload succeeds, a later pass uploads it again under a new sequenced name: the log is duplicated rather than lost. The uploader runs when a log completes and every minute. A log whose upload failed waits a minute before its next attempt, so completion notifications during a bucket outage do not retry the whole backlog on every request. When the server stops, the uploader first waits for in-flight logged requests, which `http.Server.Close` does not wait for, and then makes one last attempt at every pending log, all bounded by the shutdown context. Websocket sessions are not waited for: shutdown does not end hijacked connections, so their logs cannot complete before the process exits. An empty value keeps today's local-only behavior. A URL with the generic `key` option is rejected, because it maps every log to one object. A `file://` bucket whose objects would land in the logs directory itself (resolved as `fileblob` resolves it, including relative `file://./` roots and symbolic links) is also rejected, because the uploader would keep re-uploading its own objects; a prefix that places them in a subdirectory is accepted, since only the top level is scanned. A hot reload that changes the URL aborts the old uploader without draining it, and the new uploader picks up the files left behind. Canceling the reload abandons a bucket open that is still in progress. The bucket itself is opened with the uploader's own lifetime context, because providers may keep that context for later credential refreshes. Completing logs never wait for a bucket to open or drain.

So that a finished-looking file never holds partial content, both the non-streaming and streaming write paths now assemble the log in a `request-log-*.tmp` file. They reserve the unique `.log` name only at the end and then rename the temp file over it. An empty `.log` is therefore a reservation that has not been filled yet, and the uploader skips it. When the server starts, before it serves any requests, it deletes orphaned artifacts from requests that were still being logged when the last process stopped: `request-log-parts-*` directories, `request-body-*`, `response-body-*`, and `request-log-*` `.tmp` files, and empty reserved `.log` files. The uploader's first pass then uploads and deletes any completed logs that a previous instance stopped before uploading. This cleanup runs even without a bucket. It assumes that no other running process shares the logs directory.

Only names produced by the request logger qualify for upload, so `main.log` and its rotations stay local. Uploaded logs are no longer available through the management log endpoints, and `error-logs-max-files` only limits the error logs that are still waiting locally. This deliberate fork addition under [ADR-0003](0003-minimize-fork-divergence.md) stays within `internal/logging`, with small hooks in server construction, reload, and stop. Adding the dependency also raised several shared modules, including `fsnotify`, `golang.org/x/*`, and `google.golang.org/protobuf`, to the minimum versions that `gocloud.dev` requires.
